## Structural findings

**S-1 (STRUCTURAL): tracker `unlocked` and domain `mapStates`/`lockStates` (S10b/D47) cannot agree, and nothing connects them.**
- §8.3/§7 (and M3) say an unlocked idea stays unlocked after a publish adds a prerequisite. `packages/domain/src/lock.ts` recomputes `open` from `requires` and a `mastered` set only; it has no way to be told an idea is already unlocked.
- Probe on the merged build: v1 `b requires a`; student masters `a`; v2 adds `c` as a prerequisite of `b`. Tracker: `b.unlocked = true`. Domain `mapStates(v2 ideas, mastered={a})`: `b = "next"`. §8.4 rule 4 ("a generated view that shows a locked idea as open is rejected") would then reject a correct M4 view of `b` as open, or M4 would hide an idea the student had already unlocked, contradicting §7.
- Same family: an idea whose `requires` names an id not in the version (or itself). Tracker: never unlocks (`isMastered` of a missing id is false). Domain: ignores unknown ids, so it is `open`. Probe: `a requires ghost` → tracker `false`, domain `open`.
- Why structural: M4 will store a MapView from one function and the S2/M5 views from the other; the disagreement shows up in every map after the first publish. Fixing it after M4 and S2 wire both sides means changing both interfaces.
- No consumers of `@ideamap/tracker` exist on idea-map yet, so the fix is cheap now. Smallest fix: `mapStates`/`lockStates` take an `unlocked` set (the tracker's `progress().ideas[].unlocked`) in addition to `mastered`, with open = unlocked, and one stated rule for dangling `requires` (checks.ts already reports them to the teacher as "can never unlock"). It can land as a small domain task rather than in PR #31, but the contract should be recorded (architecture §8.4 or a decision) before M4 starts. Coordinator call whether that gates the M3 merge; under the rubric given for this review it does.

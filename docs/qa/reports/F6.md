3. **DB-level privacy functions rely on the connection's role for their second check.** `exportStudent`/`deleteStudent(db, …)` use `withOrg`, which doesn't `SET ROLE`. Called with a superuser or BYPASSRLS pool (the migration role), RLS is bypassed. *Repro:* `deleteStudent(t.db /* superuser */, {orgId: orgB, actorId: adminB, studentId: studentA1}, store)` succeeded and wiped org A's student. The same call as an `ideamap_app` login returns `not_found`. No production caller uses these wrappers: the API path goes through `scoped()`, which sets the app role, and the README says services connect as `ideamap_app`. So this is hardening, not a defect. A `SET LOCAL ROLE ideamap_app` in these wrappers, or a doc note, would make the "check again inside the transaction" claim hold regardless of the pool. Suggested weight: should.
4. Minor: `authorize` requires `role = 'student'`, so a student whose role an admin changed, for example to teacher, can no longer be FERPA-exported or deleted through these routes (404). Suggested weight: should; note for A-series admin tooling.

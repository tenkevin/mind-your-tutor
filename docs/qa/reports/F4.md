## Found during testing

1. **The event key ledger lets one org block another org's event ingest and probe its students (suggested: must, before M1/ingest).** `interaction_event_key` has no foreign key on `student_id`, the app role is granted `INSERT` on it directly, and its uniques (`id`, `(student_id, seq)`) are global, while RLS limits reads to one org. As `ideamap_app` acting for org A:
   ```
   INSERT INTO interaction_event_key(id,org_id,student_id,seq,recorded_at)
     VALUES ('01JQAQAQAQAQAQAQAQAQAQAQA1','<org A>','<org-B student>',2,now());   -- INSERT 0 1
   INSERT INTO interaction_event_key(...) VALUES (...,'<org-B student>',1,now());
     -- ERROR: duplicate key … "interaction_event_key_student_id_seq_key"   ← leaks that org-B student has seq 1
   -- then, acting for org B:
   INSERT INTO interaction_event(…,'<org-B student>', …, seq 2, …);
     -- ERROR: duplicate key … "interaction_event_key_student_id_seq_key"   ← org B's real event refused
   ```
   This needs an injection or bug in the app, but row-level security is the guard against exactly that. Suggested fix: add `FOREIGN KEY (org_id, student_id) REFERENCES app_user (org_id, id)` to `interaction_event_key`, and revoke the app's `INSERT` on the ledger. One way is to make `app.record_interaction_event_keys()` `SECURITY DEFINER` owned by the migration role, with a pinned `search_path`. Optionally, scope the uniques by `org_id`.
2. **`class_library_setting` is not class-scoped (suggested: should).** D11 says a teacher changes how the AI uses shared documents "for their class only". Uploads are class-scoped, but settings are scoped only by org. A transaction acting for class A1 can read A2's settings (the sweep above shows 1 other-class row) and write them, including which shared docs A2 has `off`. The criteria only require class scope for uploads, so this doesn't fail a check. Decide whether settings need the same `class_scope` policy, or whether the API is the guard.
3. **HNSW search under RLS may return fewer than k rows (suggested: should, for the library-search task).** An unfiltered `ORDER BY embedding <=> $v LIMIT 8` uses `chunk_embedding` with the RLS predicate applied after the index (`Rows Removed by Filter: 1` with only 2 orgs). With many orgs, HNSW's default `ef_search` of 40 candidates can leave fewer than 8 rows from the current org. Search should always filter by `curriculum_id` (that uses the btree path, as P2 shows) or enable `hnsw.iterative_scan` (pgvector ≥ 0.8).
4. **The app role can create temp tables (suggested: should, deployment).** `has_database_privilege('qa','TEMP')` = `t`, from the default `PUBLIC` grant. That isn't DDL in the app's schemas, but if the "no DDL" rule should be strict, `REVOKE TEMP ON DATABASE … FROM PUBLIC` belongs in deploy docs or a migration.
5. **No partition pruning on replay queries (info).** Hot-path queries don't filter on `recorded_at`, so every query probes every monthly partition: an index probe each, or a seq scan when the partition is empty. That's cheap now, but cost grows with retained months. This is worth recording for M1/ingest design, for example by bounding replay by snapshot time.

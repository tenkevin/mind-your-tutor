## Structural review (design, for the downstream tasks)

- **Contract:** `ingest.ts` carries only M1's events plus `textRef` text (D19 unchanged). Client-set `studentId`/`seq`/`level` are `forbidden_field`; server-only types (`teachback.judged`, `feedback.ruled`, teacher events) are refused from students. Rejection codes are an open enum a later task can add to.
- **Order and replay (M3/M4/M5):** `seq` is allocated per student by one upsert on `student_event_seq`; the row lock serialises a student's batches until commit, so no gaps or repeats. A racing resend hits the unique ledger key, rolls back the whole transaction (seq allocation included) and is judged again. `interaction_event_key` has `PRIMARY KEY (id)` and `UNIQUE (student_id, seq)`. The partition key is the server's `recorded_at`, so a client clock cannot break partitioning. Replay reads `(class_id, student_id, seq)`. Deterministic from what is stored.
- **Isolation:** all four tracker tables and the new tables use the tenant policy; a student is taken from the session, never the body; enrolment is checked for every class named or the batch is refused (403).
- **Append-only vs purge:** the only path to DELETE is a SECURITY DEFINER function, admin-only, current-org only, keyed to one student, with `search_path` pinned. The app role has no DELETE privilege on these tables.
- **S6 / q27 (practice reuses quiz events):** `question_id` accepts `practice/<exercise_id>` (`^[a-z0-9][a-z0-9_>/-]{0,299}$`), so S6 needs no contract change. Note for the future alternative (dedicated `exercise.*` events): the type is a CHECK constraint and `level` a STORED generated column frozen in migration 0016. Adding types means a new migration that drops and re-adds both, which in PG16 rewrites the partitioned log. That is slow, not breaking, and is a deliberate D19 gate.

## Non-structural (for Codex)

1. **`at` is not bounded.** `at: "0000-01-01T00:00:00Z"` passes `z.iso.datetime` and then fails in Postgres: the whole batch gets **500** (valid events in the batch lost). The queue keeps a batch the server failed on and resends it, so one such event could retry forever. Probe: `at` of 9999-12-31, 1900-01-01 and 2099-01-01 are all accepted and stored. Suggest a sane window on `at` (reject with `invalid`), because durations in M3/M4 use `at`.
2. **Cross-org id collision.** The ledger `id` primary key is global but the RLS-visible `known` lookup is per org, so an id already used in another org is not seen as taken. It fails on the unique key twice and returns 500 instead of `id_taken`. ULIDs make this practically unreachable, so only the error code is wrong.
3. **Text ownership check is by student, not class.** A `textRef` naming the same student's text stored under a different class is accepted. Harmless to the privacy rules; tidy if M3 relies on class-scoped text.

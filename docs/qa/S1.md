# QA criteria: S1 · Progress snapshots

Done when: the API serves mastery, attempts, XP, cards and Milo stage from ProgressSnapshot, and dropping the cache rebuilds identical values.
Sources: `docs/ARCHITECTURE.md` D6, D21, D24, §8.1 (snapshots), §8.3 (rulesVersion 1), §8.5; M2, M3.

## Functional

| Id | Weight | Check | Steps | Pass bar |
|---|---|---|---|---|
| S1-F1 | must | Served from snapshots | Request a student's progress after 500 events | Mastery, attempts, XP, cards and streak match a full replay of M3's rules |
| S1-F2 | must | Incremental | Add 10 events | Only events after the snapshot's seq are applied |
| S1-F3 | must | Drop and rebuild | Delete every snapshot, then request again | Byte-identical values |
| S1-F4 | must | Rules versions | Replay under a later rulesVersion | Old results stay reproducible under the old version |
| S1-F5 | should | Milo stage | If the tracker rules define Milo's stage, request it | Served from the snapshot like the other values |
| S1-F6 | must | Everything passes | Root lint, format:check, typecheck, test with DATABASE_URL (including `function_binding.test.ts`), build, plan check, on the head merged with current `idea-map` | All exit 0; CI green on the exact head |

## Security

| Id | Weight | Check | Steps | Pass bar |
|---|---|---|---|---|
| S1-S1 | must | Visibility (D21) | A student reads another student's progress; another class's teacher; another org | 403 for all. Routes declare F5 policies and are in the every-route sweep |
| S1-S3 | must | Student responses use the student view (D21; added 2026-10-30 by the coordinator from M3 QA run 2) | Inspect every student-facing response and the stored snapshot's path to it | Students receive only the tracker's student view (`progress()` student side). A raw `TrackerState`, which holds teacher-only `helpSignals` and `hints`, is never serialised to a student, by type or by test |
| S1-S2 | must | Nothing D20 forbids | Inspect the payload | No risk, engagement or ranking fields |

# QA criteria: S10b · "Next up" and "far" states from the map API

Done when: the student map API returns, for every locked idea, whether it is **next up** (one step away: every prerequisite it still needs is already open) or **far** (it needs at least one prerequisite that is itself still locked). The state is computed on the server by a deterministic, unit-tested function in `packages/domain`. The browser only draws what the API says. M4 later takes over these states in its stored MapView (§8.4), using the same function, so the meaning doesn't change.
Sources: `docs/ARCHITECTURE.md` §8.3 (idea unlocked), §8.4 (`generateMap` decides blur, lock states and highlighted next steps; a view never shows a locked idea as open), D17 (UDL), D20 (personal only, nothing ranked); S10 (`packages/domain/src/lock.ts`, `apps/api/src/routes/student-map.ts`); `project/Idea Map Explorer v2.dc.html` (the prototype's `fog` and `unconn` states, the visual reference for near and far ideas); `docs/design/README.md` (the design session draws them).

Boundary:
- In scope: the state and the API field, plus the minimum student-map change to render the two states distinctly with existing tokens (the design session refines the look).
- Out of scope: hiding titles of far ideas (a product decision; titles stay as today), anything that needs navigation history or tracker events (that's M4 and S2), and new tracker events.

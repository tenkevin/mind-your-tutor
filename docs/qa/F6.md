# QA criteria: F6 · Privacy baseline: data inventory, retention, audit log

Done when: a data inventory doc, a retention job, and `audit_event` writes on config changes and publishes.
Sources: `docs/ARCHITECTURE.md` §8.2 (InteractionText kept apart from events), §8.6 item 4, §10 (COPPA, FERPA, SOPIPA, AI transcripts with a 90-day default, audit), D6, D9, D11, and the F4 schema.

## Functional

| Id | Weight | Check | Steps | Pass bar |
|---|---|---|---|---|
| F6-F1 | must | Every stored field is inventoried | Compare `docs/privacy/data-inventory.md` with the database schema (list every table and column via `information_schema`) | Every table and column appears, with: purpose, whether it's student personal data, source, who can see it, retention period, and deletion method. A test fails if a column exists that the inventory doesn't list |
| F6-F2 | must | Retention periods are configurable per district | Inspect the retention config | Defaults: AI transcripts and typed student text 90 days (§10); other periods as the inventory states. Each can be overridden per org |
| F6-F3 | must | The retention job deletes what's due, and only that | Seed InteractionText and AiInteraction rows at 89, 90 and 91 days old for two orgs with different settings; run the job | Only rows past each org's limit are deleted. Interaction events stay intact and still replay (§8.2): text references resolve to a "removed" marker |
| F6-F4 | must | The job is safe to rerun and to interrupt | Run it twice; kill it mid-batch, then rerun | Same result, with no errors and no partial rows |
| F6-F5 | must | Audit events on config changes and publishes | Change a class's due date, a persona prompt, a rarity override and a library setting (D11); approve an AI explanation (D9); publish a version | Each writes an `AuditEvent` with actor, org, action, target, before and after values, and time |
| F6-F6 | must | Audit log is append-only | As the app role, try to `UPDATE` or `DELETE` an audit row | Refused at the database |
| F6-F7 | must | Student data export and delete (FERPA) | Request an export for one student, then a delete | Export: one file with all of that student's records in readable JSON. Delete: their personal data and text are removed, events are pseudonymised, and the action is audited |

## Security

| Id | Weight | Check | Steps | Pass bar |
|---|---|---|---|---|
| F6-S1 | must | Export and delete are restricted | Call them as a teacher, a student and an admin of another org | Only an org admin of that student's org succeeds |
| F6-S2 | must | Audit entries don't leak secrets | Change a setting whose value is sensitive (for example a connector credential) | Logged as changed, with the value redacted |
| F6-S3 | must | Deleted data is really gone | After F6-F7's delete, search every table and the export folder for the student's name and email | No matches, except the audit record of the deletion, which holds the pseudonymous id only |
| F6-S4 | should | Backups are covered | Read the inventory | It states how deleted data ages out of backups, and how long that takes |

## Performance

| Id | Weight | Check | Steps | Pass bar |
|---|---|---|---|---|
| F6-P1 | must | Retention scales | Seed 1,000,000 text rows, half of them due; run the job | Finishes in under 5 minutes, in batches, without long table locks (other inserts keep working) |
| F6-P2 | must | Audit writes don't slow requests | Time a config save with and without auditing | Under 10 ms added at p95 |

## Usability

| Id | Weight | Check | Steps | Pass bar |
|---|---|---|---|---|
| F6-U1 | must | The inventory is readable by a school | Read `data-inventory.md` | Plain English, one table per data area, and a summary a district privacy officer can check against a data processing agreement |
| F6-U2 | should | Teachers can see changes | Query the audit log for one class | A readable list of who changed what and when, ready for a Teacher Settings "History" view later |

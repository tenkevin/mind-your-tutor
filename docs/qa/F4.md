# QA criteria: F4 · Postgres schema and migrations

Done when: migrations create every entity in ARCHITECTURE.md §5 and run in CI.
Sources: `docs/ARCHITECTURE.md` §3 (one Postgres with pg-boss and pgvector), §5 (data model), §6 (layered config), §8 (append-only events, InteractionText separate, partitioned monthly), §10 (row-level security per org, retention), D9 (approved explanations per curriculum), the F3 contracts.

## Functional

| Id | Weight | Check | Steps | Pass bar |
|---|---|---|---|---|
| F4-F1 | must | Every §5 entity exists | Run migrations on an empty Postgres 16 and list the tables | Organization, User, Curriculum, CurriculumVersion, CurriculumDefaults, LibraryDoc, Chunk (with a pgvector column), Class (with `pinned_version_id`), ClassConfig, Enrollment, InteractionEvent, InteractionText, GeneratedMapView, AiOutput, ProgressSnapshot, ImportJob, ExportJob, AuditEvent, AiInteraction, a per-curriculum approved-explanation table (D9), and per-class library tables: class uploads (with chunks) and per-shared-document `use_for` settings, including `off` (D11) |
| F4-F2 | must | Keys and references are enforced | Insert rows that break each foreign key, and a duplicate `(curriculum_id, version)` | Rejected by the database |
| F4-F3 | must | Version status is constrained | Set `status` to `draft`, `published`, `archived` and `other` | Only the first three are accepted. A published version's body can't be updated (trigger or permissions) |
| F4-F4 | must | Events are append-only at the database | As the app role, try `UPDATE` and `DELETE` on `interaction_event` | Both refused. `INSERT` works. `(student_id, seq)` is unique, and so is the event `id` |
| F4-F5 | must | Events are partitioned by month | Inspect `interaction_event` | Range-partitioned by month, with a way to create next month's partition (function or migration) |
| F4-F6 | must | Extensions and queue | Check for `vector` and the pg-boss schema | Both are installed by migrations, not by hand |
| F4-F7 | must | Migrations run forwards cleanly and are repeatable | `migrate up` on empty, `migrate up` again, and (if supported) `down` then `up` | No errors; the second `up` is a no-op |
| F4-F8 | must | CI runs them | Read the CI workflow and a run | A Postgres service starts, migrations run, and a DB test suite runs on every push and PR |
| F4-F9 | must | Typed access | Inspect `packages/db` | A typed query layer or generated types; column types line up with the F3 contracts |

## Security

| Id | Weight | Check | Steps | Pass bar |
|---|---|---|---|---|
| F4-S1 | must | Row-level security per org | Create two orgs with data. As the app role, set the org context to org A and select from every tenant table | Zero rows from org B in every table. RLS is enabled and forced on all tenant tables |
| F4-S2 | must | The app doesn't run as superuser | Inspect roles | A migration role and a separate app role that has no superuser, no `BYPASSRLS` and no DDL rights |
| F4-S3 | must | Student text is separate and minimal | Inspect InteractionText and User | Typed text only in InteractionText; User holds only the fields in §10's COPPA row (name, school email, roster ids); no free-form profile fields |
| F4-S4 | must | Nothing secret in migrations | Search the migrations | No passwords, keys or real personal data; seed data, if any, is clearly fake |
| F4-S5 | should | Retention is possible | Inspect InteractionText and AiInteraction | A `created_at` and an index that make retention deletes cheap. Deleting text doesn't violate event foreign keys (§8.2) |

## Performance

| Id | Weight | Check | Steps | Pass bar |
|---|---|---|---|---|
| F4-P1 | must | Migrations are quick | Time `migrate up` on an empty database | Under 30 seconds |
| F4-P2 | must | Hot paths are indexed | `EXPLAIN` the queries: events for a student after a seq; a class's pinned version; a curriculum's versions; chunks by curriculum with vector search | Index scans, no sequential scans on tables seeded with 1,000,000 events and 10,000 chunks |
| F4-P3 | should | Event inserts are fast | Insert 100,000 events in batches of 500 | Over 5,000 rows per second on the CI runner |

## Usability (developers)

| Id | Weight | Check | Steps | Pass bar |
|---|---|---|---|---|
| F4-U1 | must | One command to a working database | Follow the README | `pnpm db:up` (or similar) starts Postgres locally (Docker compose is fine) and `pnpm db:migrate` applies everything. Both documented |
| F4-U2 | must | Schema is readable | Read the migrations | One migration per concern, with comments linking tables to ARCHITECTURE.md sections |
| F4-U3 | should | Reset for tests | Run the documented reset | A clean database in under 10 seconds |
